## Overview

Three tasks, all within the existing media-booking subsystem (Laravel `MediaBookingController` / `Assignment` + Next.js dashboards). The booking lifecycle becomes:

```
customer creates → "booking"
   coordinator Approve  → "to_assign"
       coordinator assigns student → "pending"   (existing flow)
           students accept → "confirmed"          (existing flow)
               event passes → "complete"          (existing flow)
   coordinator Reject (+reason) → "canceled"      (NEW, emails customer)
```

Key insight from exploration: the **backend already sends email + in-app + web-push notifications to all coordinators/supervisors and the customer on booking creation** (Task 2 notifications). The remaining work for Task 2 is the customer-facing "Please wait for confirmation" note + changing the initial status to the new `booking` value.

## Task 3 — Approve / Reject / Contact buttons for coordinator (list rows + detail modal)

### Backend

**Two new methods in `MediaBookingController`:**

1. `approve(MediaBooking $mediaBooking)` — guarded by `role:coordinator,supervisor,admin`.
   - Allowed only when `status === 'booking'`. Sets `status = 'to_assign'`; promotes linked Assignment to `'to_assign'`.
   - Notifies the **customer** with a new `BookingApprovedNotification` (database + mail + web-push), e.g. "Your booking for X has been confirmed and is being assigned."
   - *(Optional)* also notify other coordinators/supervisors for visibility. I'll notify coordinators/supervisors too for traceability.

2. `reject(Request $request, MediaBooking $mediaBooking)` — guarded by `role:coordinator,supervisor,admin`.
   - Requires `reason` (string, max 1000).
   - Allowed when `status === 'booking'` (also tolerate `to_assign` so a coordinator can still back out before assignment).
   - Sets `status = 'canceled'`, `cancel_reason = reason`, `canceled_by = 'coordinator'`; sets linked Assignment to `'canceled'`.
   - Notifies the **customer** with a new `BookingRejectedNotification` (database + mail + web-push, includes reason), plus the existing coordinators/supervisors (reuse `BookingUpdatedNotification` with `changeType='canceled'`).

**Two new notification classes** (mirroring existing structure, 3 channels each):
- `backend/app/Notifications/BookingApprovedNotification.php`
- `backend/app/Notifications/BookingRejectedNotification.php`

**`routes/api.php`** — add inside the `role:coordinator,supervisor,admin` group:
- `POST /media-bookings/{mediaBooking}/approve`
- `POST /media-bookings/{mediaBooking}/reject`

### Frontend

**`frontend/components/AssignmentDetailModal.tsx`**

### Decision point I'll resolve during implementation
The coordinator Assignment list is **assignment-based**, and `AssignmentController::index/show` currently eager-loads only `['creator','users']`. To show booking-level status + Approve/Reject on rows, I'll eager-load `mediaBooking` on the `Assignment` resource (`Assignment::with(['creator','users','mediaBooking'])`) and add a `mediaBooking?` field to the frontend `Assignment` type. This keeps everything on the existing assignment-centric coordinator UI rather than building a parallel bookings list.
